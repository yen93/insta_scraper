SCRIPTS
- upload_to_drive.js — CLI script. Uploads one or more local image files into
  a fixed Google Drive folder (id 1lYvSd_IpE_wL1T0clJpxt0AC6rbRvbiy, "Instagram
  Story Scraper") via the Drive v3 API, authenticating as a Google Cloud
  service account. Usage:
    node upload_to_drive.js <env|path-to-service-account-key.json> <image1> [image2 ...]
  Pass "env" as the first arg to read the key JSON from the
  GOOGLE_SERVICE_ACCOUNT_KEY_JSON environment variable (used by the scheduled
  cloud routine below), or a file path to use a key file directly (local/manual
  runs). Requires: a service account JSON key with the Drive API enabled on its
  GCP project, and that key's client_email must be shared on the target Drive
  folder (role Editor/fileOrganizer). The target folder lives inside a Shared
  Drive, so the script passes supportsAllDrives: true on the create call —
  omitting that flag causes a misleading "File not found" error even when
  permissions are correct. In "env" mode, defensively strips a literal
  "GOOGLE_SERVICE_ACCOUNT_KEY_JSON=" prefix from the env var value if present
  (see the credentials gotcha in CLAUDE.md), before JSON.parse.

- download_from_drive.js — CLI script. Downloads one or more Drive files
  straight to local paths via the Drive v3 API (drive.files.get with
  alt: 'media', supportsAllDrives: true), using the same Google Cloud service
  account as upload_to_drive.js. Usage:
    node download_from_drive.js <env|path-to-service-account-key.json> <fileId1> <outputPath1> [<fileId2> <outputPath2> ...]
  Same "env"/file-path credential convention as upload_to_drive.js, including
  the same defensive prefix-stripping. Used by the scraped_insta_stories_analyzer
  routine below to fetch each story image directly to disk, instead of the
  Google Drive MCP connector's download_file_content tool — that tool returns
  the whole file as base64 text through the model's own context, which is
  slow for every image and caused multi-minute stalls on smaller files that
  came back inline instead of auto-saving to a result file.

DATA STORES
- Supabase table public.insta_stories — columns: id, created_at, speaker,
  insta_story_image_url, insta_story_vid_url, insta_handle, status,
  description, org, event_name, poc, poc_email, poc_position,
  saved_img_link (all text, nullable except id/created_at). Populated by
  the n8n workflow below. `status` is set to 'processed' once a row's image
  has been uploaded to Drive; NULL means not yet processed.
  `description`/`org`/`event_name`/`poc`/`poc_email`/`poc_position`/
  `saved_img_link` are filled in by the scraped_insta_stories_analyzer
  routine below once it looks at the row's Drive image; `description IS
  NULL` is the marker it uses to find rows it hasn't analyzed yet
  (description is always filled once analysis completes, even when nothing
  else is identifiable — org/event_name/poc/poc_email/poc_position are left
  NULL when genuinely not identifiable in the image; saved_img_link is
  always set to the Drive file's viewUrl once that file is found, regardless
  of whether the image could be viewed directly or only analyzed via text).
- Supabase table public.speakers — columns include proper_name, batch,
  insta_handle, insta_profile_link, status. Source list of people to scrape
  Instagram stories for; owned/populated outside this project.
- Supabase table public.insta_batches_to_run — columns: batch_no,
  speaker_name, created_at, is_processed. A work queue the n8n workflow uses
  to track which (batch, speaker) pairs are due for a story-scrape pass in
  the last 24h.

EXTERNAL INTEGRATIONS (continued)
- Apify actor "Instagram Stories Scraper" (burbn/anonymous-instagram-story-

AUTOMATIONS / ROUTINES
- "insta_stories Drive Uploader" (Claude Code scheduled cloud routine, id
  trig_01LH7zt2K5iXRXeyj1Dfjpb8) — cron 0 4 * * * UTC (12:00 PM Philippines
  time daily), currently ENABLED. Queries insta_stories for status IS NULL,
  downloads each insta_story_image_url, uploads via upload_to_drive.js (env
  mode), and sets status = 'processed' only after a confirmed successful
  upload — failed rows are left NULL to retry on the next run. Attached MCP
  connector: Supabase only. Git source: this repo (main).
  Also configured as an API trigger: an API token was generated for it, and
  it can be fired on demand with `POST
  https://api.anthropic.com/v1/claude_code/routines/trig_01LH7zt2K5iXRXeyj1Dfjpb8/fire`
  (Bearer auth with that token, plus `anthropic-version` and `anthropic-beta`
  headers) — both this direct trigger and the cron schedule are active at
  the same time. This is called from the n8n workflow below (HTTP Request1
  node), chained right after a fresh scrape completes (the old standalone
  daily-fire schedule for this, Schedule Trigger2, has since been removed
  from the workflow as redundant).
  KNOWN ISSUE (partially mitigated 2026-09-08): GOOGLE_SERVICE_ACCOUNT_KEY_JSON
  on the "Default" cloud environment has previously had the literal text
  `GOOGLE_SERVICE_ACCOUNT_KEY_JSON=` prefixed onto the actual JSON value
  (the whole `KEY=value` line pasted into the value field instead of just
  the bare JSON). upload_to_drive.js now defensively strips that exact
  prefix if present, so this class of misconfiguration no longer breaks
  uploads even if the env var itself is still set wrong — but the
  underlying env var value in claude.ai/code environment settings has not
  been independently re-verified since.

- "scraped_insta_stories_analyzer" (Claude Code cloud routine, id
  trig_01QdunLBvdnu7ZK5zmYb6g35) — created 2026-09-08, now ENABLED as a pure
  API trigger (no cron_expression at all) with a generated API token, so it
  can be fired on demand with `POST
  https://api.anthropic.com/v1/claude_code/routines/trig_01QdunLBvdnu7ZK5zmYb6g35/fire`
  (same Bearer-auth pattern as the uploader routine). Called from the n8n
  workflow below (HTTP Request2 node) on its own daily schedule (Schedule
  Trigger3, 20:00 — 30 min after the main scrape-and-upload chain, to give
  uploads time to land in Drive first). Queries insta_stories for
  status='processed' AND description IS NULL, finds each row's image in the
  Drive folder by matching the "<Speaker> - story <id> - <date>.jpg" naming
  convention (Google Drive MCP connector's search_files, which also supplies
  the file's contentSnippet — Drive's own OCR text + Vision-API labels — and
  viewUrl), downloads it with download_from_drive.js (see SCRIPTS above,
  NOT the Drive MCP connector's download_file_content), views it with Read,
  and fills in description/org/event_name/poc/poc_email/poc_position/
  saved_img_link — leaving description NULL on failure so the row retries
  next run. Attached MCP connectors: Supabase + Google Drive. Allowed tools:
  Bash, Read. Git source: this repo (main). Verified working end-to-end via
  manual test runs on 2026-09-08 (last run SUCCEEDED).

- "Insta Outbound Sales Automations" (n8n workflow; export checked into this
  repo as `n8n - Insta Outbound Sales Automations.json`) — the external
  Instagram-story scraping process CLAUDE.md refers to. As of 2026-09-08 the
  old standalone/disabled duplicate entry points (the independent "Story
  scrape" schedule, the independent "fire uploader" schedule, and an
  orphaned direct-Apify HTTP node) have been removed, consolidating the
  pipeline into one continuous chain:
    1. Batch discovery (Schedule Trigger, 19:30, ENABLED) — finds distinct
       `batch` values in `speakers`, and for each one not already queued in
       the last 24h, inserts its unprocessed speakers into
       `insta_batches_to_run`.
    2. Story scrape (chained from stage 1's Limit2 output — no longer has
       its own schedule) — pulls speakers queued in `insta_batches_to_run`
       in the last 24h, batches their insta_handles into one Apify actor
       call, inserts any new insta_stories rows found, then backfills
       `speaker` names onto rows missing them, then fires the uploader
       routine above.
    3. Fire scraped_insta_stories_analyzer (Schedule Trigger3, 20:00,
       ENABLED) — calls that routine via its API trigger, independently of
       the stage 1→2 chain.
  Because stage 2 no longer has a disabled standalone entry point and is
  now only reachable via the now-enabled stage 1, the whole pipeline
  (batch discovery → Apify scrape → insert stories → fire uploader) is live
  end-to-end for the first time.
  KNOWN ISSUE (unresolved as of 2026-09-08, now more consequential since the
  chain is live): the "Execute a SQL query2" node hardcodes `batch_no = 1`
  instead of referencing the current batch from the loop it runs inside
  ($('Loop Over Items').item.json.batch), so every iteration checks batch
  1's recent-run status regardless of which batch it's actually processing.
