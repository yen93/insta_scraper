SCRIPTS
- upload_to_drive.js — CLI script. Uploads one or more local image files into
  a fixed Google Drive folder (id 1lYvSd_IpE_wL1T0clJpxt0AC6rbRvbiy, "Instagram
  Story Scraper") via the Drive v3 API, authenticating as a Google Cloud
  service account. Usage:
    node upload_to_drive.js <env|path-to-service-account-key.json> <image1> [image2 ...]
  Pass "env" as the first arg to read the key JSON from the
  GOOGLE_SERVICE_ACCOUNT_KEY_JSON environment variable (used by the scheduled
  cloud routine below), or a file path to use a key file directly (local/manual
  runs). Requires: a service account JSON key with the Drive API enabled on its
  GCP project, and that key's client_email must be shared on the target Drive
  folder (role Editor/fileOrganizer). The target folder lives inside a Shared
  Drive, so the script passes supportsAllDrives: true on the create call —
  omitting that flag causes a misleading "File not found" error even when
  permissions are correct.

DATA STORES
- Supabase table public.insta_stories — columns: id, created_at, speaker,
  insta_story_image_url, insta_story_vid_url, insta_handle, status,
  description, org, event_name, poc, poc_email, poc_position (all text,
  nullable except id/created_at). Populated by the n8n workflow below.
  `status` is set to 'processed' once a row's image has been uploaded to
  Drive; NULL means not yet processed. `description`/`org`/`event_name`/
  `poc`/`poc_email`/`poc_position` are filled in by the
  scraped_insta_stories_analyzer routine below once it looks at the row's
  Drive image; `description IS NULL` is the marker it uses to find rows it
  hasn't analyzed yet (description is always filled once analysis
  completes, even when nothing else is identifiable — the other five
  columns are left NULL when genuinely not identifiable in the image).
- Supabase table public.speakers — columns include proper_name, batch,
  insta_handle, insta_profile_link, status. Source list of people to scrape
  Instagram stories for; owned/populated outside this project.
- Supabase table public.insta_batches_to_run — columns: batch_no,
  speaker_name, created_at, is_processed. A work queue the n8n workflow uses
  to track which (batch, speaker) pairs are due for a story-scrape pass in
  the last 24h.

EXTERNAL INTEGRATIONS (continued)
- Apify actor "Instagram Stories Scraper" (burbn/anonymous-instagram-story-

AUTOMATIONS / ROUTINES
- "insta_stories Drive Uploader" (Claude Code scheduled cloud routine, id
  trig_01LH7zt2K5iXRXeyj1Dfjpb8) — cron 0 4 * * * UTC (12:00 PM Philippines
  time daily), currently ENABLED. Queries insta_stories for status IS NULL,
  downloads each insta_story_image_url, uploads via upload_to_drive.js (env
  mode), and sets status = 'processed' only after a confirmed successful
  upload — failed rows are left NULL to retry on the next run. Attached MCP
  connector: Supabase only. Git source: this repo (main).
  Also configured as an API trigger: an API token was generated for it, and
  it can be fired on demand with `POST
  https://api.anthropic.com/v1/claude_code/routines/trig_01LH7zt2K5iXRXeyj1Dfjpb8/fire`
  (Bearer auth with that token, plus `anthropic-version` and `anthropic-beta`
  headers) — both this direct trigger and the cron schedule are active at
  the same time. This is called from the n8n workflow below (HTTP Request1
  node) both on its own schedule (Schedule Trigger2) and right after a fresh
  scrape completes.
  KNOWN ISSUE (unresolved as of 2026-09-08): GOOGLE_SERVICE_ACCOUNT_KEY_JSON
  on the "Default" cloud environment currently has the literal text
  `GOOGLE_SERVICE_ACCOUNT_KEY_JSON=` prefixed onto the actual JSON value
  (the whole `KEY=value` line was pasted into the value field instead of
  just the bare JSON). A run on 2026-09-08 only succeeded because the
  routine detected this mid-run and stripped the prefix for that session
  only — the fix was never persisted to the actual env var, so the next run
  that finds real rows to upload will fail identically to the original
  credential bug unless this is corrected in claude.ai/code environment
  settings (value should be ONLY the raw `{...}` JSON, no `KEY=` prefix).

- "scraped_insta_stories_analyzer" (Claude Code cloud routine, id
  trig_01QdunLBvdnu7ZK5zmYb6g35) — created 2026-09-08, currently DISABLED
  with an inert placeholder cron (0 5 * * *) and no API trigger token yet
  generated (the create API has no field for that; it's a manual step in
  claude.ai/code UI, same as the uploader routine's token). Queries
  insta_stories for status='processed' AND description IS NULL, finds each
  row's image in the Drive folder by matching the "<Speaker> - story <id> -
  <date>.jpg" naming convention (Google Drive MCP connector's search_files),
  downloads and views it (download_file_content + base64 decode + Read),
  and fills in description/org/event_name/poc/poc_email/poc_position —
  leaving description NULL on failure so the row retries next run. Attached
  MCP connectors: Supabase + Google Drive. Allowed tools: Bash, Read. Git
  source: this repo (main). Never fired as of creation — all 11 existing
  rows are still pending and will be backfilled on its first run (manual
  `RemoteTrigger action: "run"`, or once enabled/API-triggered via its
  claude.ai/code page).

- "Insta Outbound Sales Automations" (n8n workflow; export checked into this
  repo as `n8n - Insta Outbound Sales Automations.json`) — the external
  Instagram-story scraping process CLAUDE.md refers to. Three stages:
    1. Batch discovery (Schedule Trigger, DISABLED) — finds distinct `batch`
       values in `speakers`, and for each one not already queued in the last
       24h, inserts its unprocessed speakers into `insta_batches_to_run`.
    2. Story scrape (Schedule Trigger1, DISABLED) — pulls speakers queued in
       `insta_batches_to_run` in the last 24h, batches their insta_handles
       into one Apify actor call, inserts any new insta_stories rows found,
       then backfills `speaker` names onto rows missing them.
    3. Fire Claude routine (Schedule Trigger2, ENABLED) — calls the routine
       above via its API trigger.
  KNOWN ISSUES (unresolved as of 2026-09-08):
    - Only stage 3 is actually scheduled; stages 1-2 (which populate new
      insta_stories rows) are both disabled, so nothing currently feeds the
      routine new rows automatically unless run manually in n8n.
    - The "Execute a SQL query2" node hardcodes `batch_no = 1` instead of
      referencing the current batch from the loop it runs inside
      ($('Loop Over Items').item.json.batch), so every iteration checks
      batch 1's recent-run status regardless of which batch it's actually

  Also contains an apparently-orphaned standalone "HTTP Request" node (calls

  REST) with no incoming connection in the workflow — looks like a leftover
